# Benchmark: cluster profile on kind (2026-09-13)

First end-to-end validation of the `cluster` deployment profile on a real multi-node Kubernetes
cluster, followed by scaling and chaos experiments ([04-cluster.md](../../plan/04-cluster.md) test
strategy). Setup runbook: [kind-dev-cluster.md](../kind-dev-cluster.md).

> **Laptop numbers.** Every node, broker, ClickHouse server and load generator shares one
> 10-CPU / 16 GiB Docker VM, and ingest/processor pods were deliberately capped at 300m CPU. The
> absolute rates say nothing about the 50k/s-per-pod production target. What they show is how
> throughput scales with replicas, where the bottleneck is, and whether anything is lost.

## Summary

- The chart came up on kind after three deployment fixes (Strimzi 1.x API version, StorageClass,
  Altinity watch namespace). Schema `ON CLUSTER` on both shards, topics per kafka.md, `/readyz` 200,
  sharding and the query API all verified.
- **No acknowledged data was lost in any run**, including a 20-minute processor crash loop, a
  17-minute ClickHouse memory livelock and the chaos tests (see [Chaos](#chaos)). Duplicates appeared
  only when processors were killed or restarted repeatedly while holding uncommitted batches
  (0.67-1.36%); single graceful or forced kills produced none.
- **Chaos under load** (Kafka broker, ClickHouse pod, processor graceful and forced, ingest pod):
  0 loss and 0 duplicates in every test; recovery 6-27 s. Only the ingest kill was client-visible
  (250 x 503, plus 378 x 503 during an ingest rollout); after chart fixes to ingest draining and Envoy
  retries/ejection, an ingest pod kill **and** a full ingest rollout under load gave **0** errors.
- **Ingest** is CPU-bound and stateless: one 300m pod accepted ~106k items/s; two pods absorbed the
  whole 120k items/s offered load at ~218m each.
- **Processor scaling stops at ~1.4x.** 1 processor: 55k rows/s (CPU-bound). 2 processors: 78k rows/s
  with CPU to spare. 4 processors: no further gain, processors ~46% busy. The limit is the
  ClickHouse **Distributed insert path**: coordinator insert p50 ~580 ms vs ~80 ms for the per-shard
  local inserts behind it, and all coordination landed on one ClickHouse pod.
- Real bugs fixed: processor OOM/crash loop on any consumer-lag backlog (unbounded fetch
  buffering + unbounded batch within a poll), processor retries in lockstep, Keeper pods not spread,
  dev sizing that livelocks ClickHouse. Details in [Bugs found and fixed](#bugs-found-and-fixed).

## Method

- **Load:** `openlog-loadgen` as Kubernetes Jobs on the control-plane node, OTLP/HTTP protobuf+gzip
  through Envoy (`http://openlog-envoy:4318`), 200 hosts per job, 32 concurrent requests, 10 s host
  metrics, 1 min inventory. One job = 20k logs/s (100 per request) + 20k spans/s (one request per
  second) + ~800 datapoints/s. Fixed offered load: **3 jobs = ~120k items/s** for 150 s. Each run uses
  its own host prefix so rows can be attributed.
- **Fixed-size pods:** ingest and processor limited to 300m CPU so a single replica saturates on the
  laptop (unlimited, one ingest pod used only ~130m at 40k items/s).
- **Measured:** loadgen totals (only HTTP 200 counts as accepted; loadgen does not retry); consumer
  lag sum (Kafka); ClickHouse row counts every ~10 s; `kubectl top` per pod; ClickHouse `query_log`
  insert latency; lag drain time after the jobs end.
- **Loss / duplicates:** per run, stored vs accepted. Spans: exact `uniqExact(trace_id, span_id)`.
  Datapoints: unique `(metric, timestamp, attributes, host)`. Logs: loadgen log records have no
  unique id, so only `stored - accepted` is meaningful (>= 0 means no loss unless offset by duplicates;
  spans, which are exact, never showed loss).
- Steady state = 40 s after start until the jobs finish.

### Bottleneck analysis

1. **Ingest: CPU.** Pinned at its limit while Kafka, Envoy and processors had headroom. Add replicas.
2. **1 processor: processor CPU** (265m of 300m) - decode + row building + upload.
3. **>= 2 processors: the ClickHouse Distributed insert.** Processor CPU drops below the limit and
   stored rows/s stops following the replica count, while ClickHouse coordinator CPU grows. With
   `distributed_foreground_insert=1` every batch is uploaded to one server, split by sharding key and
   synchronously forwarded; the coordinator spends ~7x the time of the per-shard inserts. Because
   `OPENLOG_CLICKHOUSE_ADDR` is the single ClickHouse Service and the driver keeps long-lived
   connections, kube-proxy pinned 88-100% of coordination to one pod.
4. **Kafka: not a bottleneck** (brokers 240-300m, produce p50 ~12 ms, no ISR shrink under load).
5. **ClickHouse memory (dev sizing).** ClickHouse caps itself at 90% of the pod limit, measured
   against RSS. With 2Gi and ~50M rows stored, RSS sat at 1.8 GiB (tracked query memory only
   280-500 MiB, the rest caches); every insert then failed with `MEMORY_LIMIT_EXCEEDED`.

## Chaos

Fresh install (final image and values), 2 ingest + 4 processors, constant load of 2 loadgen jobs
= ~60k items/s (15k logs + 15k spans per job) for 240 s, victim deleted at +60 s. Recovery = until the
replacement pod is Ready (StatefulSet pods: new UID and ready; Deployments: old pod gone and all
replicas ready). Lag was read from the Strimzi Kafka exporter.

| Test | Victim | Client-visible errors | Recovery (pod Ready) | Lag / throughput impact | Accepted = stored | Loss | Duplicates |
|---|---|---|---|---|---|---|---|
| (a) Kafka broker | `openlog-dual-1` (graceful delete) | **0** | 27 s | none visible: stored 54-70k rows/s throughout, lag < 2.2k records | logs 7,175,250; spans 7,170,000; datapoints 385,560 | **0** | **0** |
| (b) ClickHouse pod (shard 2 of 2, 1 replica) | `chi-openlog-openlog-1-0-0` | **0** | 19 s | inserts failed ~5-7 s (6 failed attempts per processor, same tokens), lag peak 5.3k records, back to normal within ~20 s | logs 7,182,600; spans 7,185,000; datapoints 389,160 | **0** | **0** |
| (c1) Processor, graceful | 1 of 4 processors | **0** | 6 s | no visible dip (flush + commit on SIGTERM) | logs 7,152,975; spans 7,185,000; datapoints 387,120 | **0** | **0** |
| (c2) Processor, forced (`--grace-period=0 --force`) | 1 of 4 processors | **0** | pod object gone at once; group rebalanced | uncommitted records (<= 2 s flush interval) redelivered to other members | logs 6,932,850; spans 7,110,000; datapoints 386,640 | **0** | **0** |
| (d) Ingest pod, before fix | 1 of 2 ingest pods | **250 x HTTP 503** (0.23% of requests), all within 10 s of the kill | 9 s | none on the processing side | logs 7,156,425; spans 7,185,000; datapoints 387,280 (503-rejected requests excluded) | **0** | **0** |
| (d) Ingest, first fix only (preStop 15 s + route retries) | 1 of 2 ingest pods | 2 after the kill, but **378 x 503** in the first 10 s right after an ingest rollout | 20 s | none on the processing side | logs 7,162,725; spans 7,170,000; datapoints 384,080 | **0** | **0** |
| (d) Ingest, final fix: pod deleted at +60 s **and** `rollout restart` of ingest at +150 s | 1 of 2 ingest pods, then all | **0** | 24 s (pod); rollout 8 s | none | logs 7,085,325; spans 7,110,000; datapoints 387,920 | **0** | **0** |

Notes:

- (a) RF=3 / `min.insync.replicas=2` / `acks=all`: producers kept succeeding with 2 replicas and the
  consumer group did not lose progress.
- (b) Killing a ClickHouse pod with 1 replica per shard makes every insert fail while it is gone
  (the Distributed insert needs all shards). The processor retried the same batches with the same
  deduplication tokens, committed nothing meanwhile and lost or duplicated nothing. Queries touching
  shard 2 fail during that window.
- (c) Neither kill produced duplicates: a duplicate requires a kill between a successful insert and
  the offset commit (milliseconds). They did occur with repeated kills during long insert retries
  (see the unplanned failures below).
- (d) **Root cause of the 503s (chart bug, fixed):** Envoy stats show `upstream_cx_connect_fail` 244
  and `upstream_rq_pending_failure_eject` 250 for `ingest_http` - exactly the 250 client errors.
  Ingest slept only 5 s in `preStop` before closing its listener, while Envoy needs up to ~15 s to
  drop the endpoint (2 failed health checks x 5 s, DNS refresh 5 s), and the route had no retry.
  First fix: `ingest.preStopSleepSeconds: 15` and an Envoy `retry_policy` limited to
  `connect-failure,refused-stream,reset-before-request` (requests that never reached ingest, so a retry
  cannot produce twice) on a different host (`previous_hosts`). The rerun cut the kill itself to 2
  errors but exposed a second problem: right after an ingest rollout, 378 requests failed because
  Envoy kept connecting to removed pods (`STRICT_DNS` behind kind's 30 s CoreDNS cache) and the
  cluster circuit breaker (`max_retries: 3`) rejected the retries (`upstream_rq_retry_overflow` 376).
  Final fix: `retry_budget` (25% of active requests, min 10) plus local-origin outlier ejection after
  2 connection failures. With it, an ingest pod kill and a full ingest rollout under load produced
  0 client errors (Envoy: 6 connection failures, 6 successful retries, 0 overflow).
  Loadgen does not retry; real OTLP clients (and the infra agent's disk buffer) retry 503 +
  `Retry-After`, so none of these were data loss.

## Bugs found and fixed

| # | Area | Bug and root cause | Fix | Test |
|---|---|---|---|---|
| 1 | processor / Kafka client | **Processor OOM / crash loop whenever it starts on a consumer-lag backlog.** franz-go buffers one fetch per broker in parallel and decompresses it into records on arrival; `FetchMaxBytes(64 MiB)` counts compressed bytes and OTLP zstd expands ~5x, so 3 brokers => >1 GiB before the first insert. Restarting re-polls the same backlog: permanent stall (and data loss once retention expires). | `internal/queue`: `FetchMaxBytes = MaxMessageBytes + 1 MiB` (kgo clamps partition bytes to it, so one max-size record still fits), `MaxConcurrentFetches = 2` | `TestConsumerClientBoundsFetchBuffering` |
| 2 | processor | A poll of up to 10,000 records was fully decoded before `BatchRows` was checked (millions of rows in memory). | `Processor.Run` flushes + commits as soon as the batch reaches `BatchRows`, also mid-poll; processed records are released; shutdown semantics unchanged | `TestRunFlushesWithinOnePollAtBatchRows` (bounded inserts, tokens, commit after each batch) |
| 3 | processor | Insert retries use deterministic exponential backoff, so processors that fail together (ClickHouse overload) retry in lockstep. | Full jitter in `[d/2, d]` | `TestJitterBoundsAndSpread` |
| 4 | chart | Go runtime unaware of the container memory limit. | `GOMEMLIMIT` from `resourceFieldRef: limits.memory` for all openlog containers | render + server dry-run |
| 5 | chart | Keeper pods had no anti-affinity; all 3 landed on one node (one node failure = no quorum = no Replicated inserts / DDL). | default soft hostname anti-affinity unless `clickhouse.altinity.keeper.affinity` is set | render |
| 6 | chart | Strimzi 1.x rejects `v1beta2` CRs. | default `kafka.strimzi.io/v1` | dry-run + install |
| 8 | chart (ingest + Envoy) | Deleting an ingest pod under load gave 250 client 503s; an ingest rollout gave 378. Ingest closed its listener after a 5 s `preStop` sleep while Envoy still routed to it (health checks 2 x 5 s; `STRICT_DNS` behind a CoreDNS cache of 30 s), the route had no retry, and the cluster circuit breaker allowed only `max_retries: 3` (Envoy: `upstream_rq_retry_overflow` 376). | `ingest.preStopSleepSeconds: 15`; route `retry_policy` on `connect-failure,refused-stream,reset-before-request` (never reached ingest, so no double produce) with `previous_hosts`; `retry_budget` (25%, min 10) instead of `max_retries: 3`; local-origin outlier ejection after 2 connection failures | Envoy `--mode validate`; chaos (d): pod kill + full ingest rollout under load -> 0 errors (6 connect failures, 6 successful retries) |
| 7 | values-dev | k3s-only StorageClass; processor 1Gi too small for 50k-row batches; ClickHouse 2Gi + default 5 GiB mark cache livelocks inserts. | `storageClass: ""`; processor limit 2Gi; ClickHouse 3Gi + `mark_cache_size: 268435456` | install + reruns |

Bug 1 was the root cause of the first "processor scaling" run never draining; bugs 1-3 together
turned a stall into a bounded, recoverable backlog. Bug 3 alone did not end the ClickHouse livelock
(the server was simply out of memory); it removes the synchronized retry storm.

## Operational findings

- **Helm 4 server-side apply** conflicts with `kubectl scale`: the next `helm upgrade` fails on
  `.spec.replicas` and leaves a `failed` revision with some objects already changed. Use values or
  `--force-conflicts`.
- **Never run Kafka CLI tools inside broker pods** in a tight loop: each `kafka-consumer-groups.sh`
  starts a JVM inside the broker's 1Gi memory cgroup; the kernel OOM-killed the broker JVM itself.
  Use the Strimzi Kafka exporter (`kafka_consumergroup_lag`) or a separate client pod.
- **Retention is the loss boundary of a stalled pipeline.** The processor consumer uses
  `ConsumeResetOffset(AtStart)`: if a backlog outlives `retention.ms`, the group's offsets fall out of
  range and consumption silently restarts at the earliest retained record. During the livelock the
  30-min benchmark retention came within ~10 minutes of deleting acknowledged, unconsumed data.
- **Disk:** kind nodes share the Docker VM disk; high-rate runs plus 24h retention filled it, crashing
  etcd and then every broker. Keep an eye on broker and ClickHouse volumes in any shared environment.
- **Keeper placement** cannot be fixed by affinity after the fact when volumes are node-local. On a
  fresh install with the new chart default the 3 Keeper pods landed on 3 different nodes.
- **Reinstall in operators mode can come up without topics.** `helm uninstall` removes the Kafka
  cluster (and its Topic Operator) while the `KafkaTopic` objects still wait for the operator's
  finalizer. A `helm install` right after applied onto those terminating objects; the new Topic
  Operator then completed their deletion. Result: release `deployed`, every pod Ready, **no topics**,
  and every OTLP request answered 503 (`UNKNOWN_TOPIC_OR_PARTITION`). A `helm upgrade` recreated them.
  Ingest `/readyz` only checks broker connectivity, so readiness did not catch it. Recommendation:
  make ingest readiness (and processor start-up) verify that the three topics exist, and wait for
  `KafkaTopic` objects to be gone before reinstalling.
- **Strimzi 1.x Kafka exporter** has no Service and listens on 9404 (`port-forward deploy/<kafka>-kafka-exporter`);
  it reports lag -1 for partitions without a committed offset.

## Recommendations for the open questions in 04-cluster.md

### 1. Distributed vs. direct shard insert

**Recommendation: move the processor to direct shard inserts before M1 load tests on real hardware.**

- Evidence: from 2 processors on, throughput stopped scaling while processors had idle CPU; the
  Distributed coordinator spent ~7x the per-shard insert time (p50 ~580 ms vs ~80 ms) and 88-100% of
  coordination landed on one pod. The coordinator also holds each whole batch in memory, which
  contributed to the ClickHouse memory livelock.
- Design: the processor computes the shard with the same key as the Distributed table
  (`cityHash64(tenant_id, host_id)` / `cityHash64(tenant_id, trace_id)` modulo total shard weight, read
  from `system.clusters`), keeps one connection pool per shard (all replicas of that shard), and
  writes `*_local` tables. The deduplication token becomes `<kafka.md token>:<shard_num>`, which is at
  least as strict as today's (a Distributed insert already dedups per shard sub-block).
- Cheap interim step (config only): list every ClickHouse pod in `OPENLOG_CLICKHOUSE_ADDR` instead of
  the Service so coordination spreads over all servers (the driver round-robins addresses).
- Keep the Distributed tables for reads.

### 2. Duplicates after rebalance / restarts

- Measured under ~60k items/s: a graceful processor kill (flush + commit on SIGTERM) and a forced
  kill (`--grace-period=0 --force`, group rebalance, redelivery of up to one flush interval) both
  produced **0** duplicates. A duplicate needs a kill between a successful insert and the offset
  commit, a window of milliseconds. Duplicates did appear with repeated kills/restarts while insert
  retries ran for minutes: spans 0.67% after an OOM crash loop, logs 1.36% after restarting processors
  during a ClickHouse memory outage. Loss was 0 in every case.
- M0 decision stands: accept small duplicates. Two improvements worth scheduling:
  1. Make batch boundaries independent of poll timing, so a redelivered range produces the same
     tokens: e.g. cut per-partition batches at offsets that are multiples of N records (or carry the
     last flushed offset range per partition in the token), so retries after a restart deduplicate.
  2. Where exact counts matter (tail sampling, M2+), use `ReplacingMergeTree`/`FINAL`-free dedup on
     `(tenant_id, trace_id, span_id)` for spans.
- Also flush and commit in an `OnPartitionsRevoked` hook, so a revoked member that is still alive
  never re-inserts with different boundaries.

### 3. Processor and partition sizing

- **Processor capacity:** one processor at 300m CPU stored ~55k rows/s (~180k rows per CPU-second)
  while ClickHouse kept up. Size processors on CPU only until ClickHouse insert latency rises; beyond
  that (here: > 1 processor per shard) more processors add nothing with Distributed inserts.
- **Memory:** 50k-row log/span batches peak near 1 GiB; give processors >= 2 GiB (production values use
  4 GiB) or lower `OPENLOG_PROCESSOR_BATCH_ROWS`.
- **Partitions:** 12 partitions were never the limit here; keep `partitions = 2-4x steady-state
  processors` (cluster default 48) so scaling does not require repartitioning.
- **Alerting:** alert on lag in *seconds* (lag records / consumption rate) against `retention.ms`
  (e.g. warn at 25% of retention), and on `openlog_processor_insert_failures_total` rate; both
  stalls in this run were silent otherwise.
- **ClickHouse:** size memory for merges and caches, not just queries; on small nodes set
  `mark_cache_size` explicitly. Shards are the write-capacity unit once direct inserts remove the
  coordinator bottleneck.
